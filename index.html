What a test automation framework is

A framework is the shared structure around your tests. It lets many people write tests the same way, on web, mobile, desktop and API.

What it is

There are three levels. Many people mix them up.

Test script
Automates one check. For example: "a customer can log in."
Test suite
A group of related scripts. For example: all login and checkout tests.
Framework
The structure every script uses: configuration, drivers, page objects, test data, waits, hooks, reports and CI.

Why you need it

Without a framework, each test repeats the same setup. URLs, locators, passwords and waits get copied into hundreds of files. Then one small UI change breaks hundreds of tests, and nobody trusts the results.

With a framework, each piece of knowledge lives in one place. A locator lives in one page object. A URL lives in one config file. A wait lives in one driver adapter. Change it once and every test gets the fix.

How this guide works

Every topic follows the same order, so you always know where you are:

  1. Read what it is and why it matters.
  2. See a diagram or a small interactive example.
  3. Code the same idea in C#, TypeScript, Python and Java. Pick your language once at the top of the page.
  4. Watch out for the common mistakes.

The reference stack is Playwright for web and API, Appium for Android, iOS and Windows desktop, and each language's normal test runner. Reqnroll, Cucumber and pytest-bdd are optional for BDD.

Build order: start small, grow on purpose

You do not need every pattern on day one. Build in this order and stop at each step until it works.

Why the order matters

Teams often build ten base classes and a custom report before they have one working test. That framework is hard to learn and hard to change. A working smoke test in CI on day two teaches you more than any design document.

See it

  1. List platforms and risksWeb? Android? iOS? Windows desktop? API? Which flows would hurt most if they broke?
  2. Choose one language and one runnerPick what your team already maintains with confidence.
  3. Write one smoke test that runs locallyOpen the app and check one thing. Nothing else.
  4. Add validated configurationBase URL and platform from the environment. Fail fast when something is missing.
  5. Add page objects when duplication appearsThe second time you copy a locator, move it into a page.
  6. Create and clean up test dataUnique data per test, created through the API.
  7. Capture failure evidenceScreenshot, trace and log on failure, in one output folder.
  8. Run the same command in CIIf CI runs a different command than you do, results will differ.
  9. Add parallel runs after tests are isolatedParallel runs expose shared state. Fix isolation first.
  10. Add patterns only for real problemsFacade, strategy, observer: add each one when you can describe the pain it removes.

Milestone: a new teammate can clone, install, configure, run the smoke test and read a failure, without asking anyone for hidden rules.

The test pyramid: choose the right level

Test each behavior at the lowest level that gives you enough confidence.

What it is

The pyramid is a picture of a healthy test mix. The bottom has many fast, cheap tests. The top has a few slow, realistic ones.

Why you need it

UI tests are slow and break more easily, because they depend on the browser, the network, the layout and the data. If most of your tests are UI tests, the suite becomes slow and flaky. This is often called an "ice-cream cone," the pyramid upside down.

See it: click a level

How to choose the level

For each behavior, ask these questions in order. Stop at the first "yes."

  1. Can a unit test check it completely? Use a unit test.
  2. Can an API, component or contract test check it? Use that.
  3. Does it need a real browser, device or full user journey? Use a UI or end-to-end test.
  4. Does automating it cost more than the risk it removes? Keep it manual or exploratory.

Discount calculationUnit or API

Watch out

  • The pyramid is a guide, not a quota. A microservice platform may need more contract tests. A content site may need more visual and accessibility checks.
  • Do not test business rules through the UI when the API can check them in milliseconds.

Risk analysis: decide what to automate first

You can never automate everything. Risk analysis tells you where your effort protects the most.

What it is

Risk is two things multiplied together:

Risk = Likelihood × Impact

Likelihood is how likely the feature is to break. Complex code, frequent changes, new developers and third-party dependencies raise it. Impact is how bad it is when it breaks. Lost money, blocked users, legal problems and data loss raise it.

Why you need it

Without risk analysis, teams automate what is easy, not what matters. They end up with 200 tests for the profile page and none for refunds. Risk analysis also gives you a clear answer when a manager asks, "Why did you test this and not that?"

How to do it

  1. List features and flows. Use the user stories, the menu, or the API list.
  2. Score each one from 1 to 5 for likelihood and for impact. Do it with a developer and a product person, not alone.
  3. Multiply the two scores. Sort from highest to lowest.
  4. Decide the depth for each band: high risk gets several levels of tests on every pull request, low risk may stay manual.
  5. Review the scores every release. Risk changes when code changes.

  • Do not score alone. QA sees likelihood well. Product sees impact well. You need both.
  • A high score does not always mean "more UI tests." It often means "more API and unit tests, plus one end-to-end journey."

What "hybrid framework" means

A hybrid framework mixes several styles of automation and several platforms in one shared structure.

What it is

"Hybrid" has two meanings, and a modern framework usually has both:

Hybrid in style
It combines a modular design (page objects, facades), data-driven tests (one test, many rows from JSON or Excel), and optional BDD (Gherkin feature files on top).
Hybrid in platform
One framework drives web (Playwright), mobile (Appium for Android and iOS), desktop (Appium Windows driver, or FlaUI and pywinauto) and API tests.

Why you need it

Many products have a web app, a mobile app and an admin desktop tool that all share the same business flows. If you build three separate frameworks, you write login, test data, config and reporting three times. In a hybrid framework, the business layer is written once and only the bottom layer changes per platform.

See it: one test, many platforms

How to do it

  1. Write tests against business actions (facades), not against screens.
  2. Give each platform its own page objects, because screens differ.
  3. Hide each automation tool behind one small driver interface. Playwright and Appium become two adapters.
  4. Pick the platform at runtime from configuration (PLATFORM=android), using a factory.

Watch out

  • Do not force one page object to serve every platform with if (android) ... else ... inside every method. Use one page class per platform, behind one interface.
  • For desktop: Microsoft's WinAppDriver, which the Appium Windows driver uses, is no longer actively developed. Check its status before you commit to it. FlaUI (C#) and pywinauto (Python) are common alternatives. For Electron apps, Playwright can drive the app directly.

Layered architecture and the dependency rule

Each layer has one job. Calls only go downward.

What it is

The framework is a stack of layers. A layer may call the layers below it, never the layers above. Some parts, like configuration and logging, are used by every layer. These are called cross-cutting concerns.

Why you need it

When calls go in every direction, a change anywhere can break anything. With one direction, you know exactly what a change can affect. A locator change touches only the page layer. A switch from Appium to another tool touches only the driver layer.

See it: click a layer

Rules to follow

  • Tests describe behavior and check outcomes. No locators, no URLs, no sleeps.
  • Step definitions (BDD only) translate Gherkin into calls. No logic.
  • Facades run business flows across several pages or APIs.
  • Pages own locators and screen actions.
  • Drivers own the automation tool and the waiting.
  • Pages may expose technical checks like expectLoaded(). Business checks stay visible in the test, so a reader can see what is being tested.
  • A facade may skip layers when that is its documented job. For example, it may use an API client for setup. Do not force every call through every layer.

Folder structure and naming

The folder tree is the architecture you can see. A new person should guess where a file lives without asking.

What it is

The structure keeps three things apart: reusable framework code, tests, and data and output. Inside the framework, each folder matches one layer or one pattern. Web, mobile and desktop each get their own subfolder where they really differ: drivers and pages.

Why you need it

When framework code and tests are mixed, people copy helpers into test files and the framework slowly rots. A clear tree also makes code review easy: "Why is there a locator in tests/?"

System design principles for test code

The same rules that keep large software systems healthy also keep a test framework healthy.

What they are

Principles are rules of thumb, not laws. Each one answers a simple question about your code. Some are about how you write classes, like SRP and DRY. Others are qualities the whole framework should have, like scalability and observability.

Why you need them

Test code grows fast. A suite of 100 tests becomes 2,000 in a year. Without principles, every new test makes the next one harder to write. With them, the cost of a new test stays small.

SOLID in a test framework

Five object-oriented principles, each shown with a piece of this framework.

What it is

S

Single responsibility

One reason to change. LoginPage changes only when the login screen changes.

O

Open / closed

Add behavior with new classes, not by editing old ones. A new SSO login is a new strategy.

L

Liskov substitution

A subtype must work wherever its parent works. Every LoginView can log in, on any platform.

I

Interface segregation

Keep interfaces small. Desktop apps have no URLs, so goTo() is not in the base driver interface.

D

Dependency inversion

Depend on interfaces. LoginFacade needs "a login strategy," not one specific class.

Why it matters here

SOLID is what makes the hybrid idea work. Because pages depend on a driver interface (D), you can plug in Playwright or Appium. Because the interface is small (I), a desktop adapter does not have to fake a "go to URL" method it cannot support. Faking it would break L.

Configuration, environments and secrets

One place answers "where am I running, on which platform, against which URL?"

What it is

A config manager loads settings once and gives the same object to every part of the framework. That is the Singleton pattern. Settings come from several places. A later source overrides an earlier one:

  1. Safe defaults in code
  2. A non-secret environment file, such as config/qa.env
  3. Environment variables (local .env or CI)
  4. Command-line arguments

Why you need it

The same tests must run on QA, staging and sometimes production, on web and on devices. If URLs and platforms are written inside tests, you need a different copy of every test for each environment. With config, you change one variable.

How to do it

  1. Use the same variable names in every language: BASE_URL, PLATFORM, APPIUM_URL, APP_PATH.
  2. Fail fast: if a required value is missing, stop with a clear message before any test runs.
  3. Keep secrets out of files that Git tracks. Locally, use a git-ignored .env. In CI, use the secret store.

This is the heart of a hybrid framework: one small interface, one adapter per tool, one factory that picks.

What it is

A driver interface lists what any platform can do: click, type, read text, wait until visible, take a screenshot. An adapter implements it with a real tool. The Playwright adapter drives browsers. The Appium adapter drives Android, iOS and Windows apps. The factory reads the config and returns the right adapter.

Why you need it

  • No test or page creates a driver directly. If driver creation changes (a device cloud, new capabilities), you edit one file.

  • Each tool's quirks stay inside its adapter. Appium has no auto-wait, so its adapter adds the waits (see topic 23).

Base page and the Template Method pattern

The base page fixes the steps every page follows. Each page fills in only its own details.

What it is

Template Method means a parent class defines the order of steps, and child classes fill in some of the steps. Here, "open a page" is always: navigate, then wait until the page is ready. A web page navigates by URL. A mobile screen may already be open. Both wait for their own "ready marker."

Why you need it

Without it, some pages wait after opening and some do not. Tests then fail randomly on slow machines. With a template, "open, then wait until ready" happens the same way everywhere, and nobody can forget the wait.

Page Object Model (POM) across platforms

A page object is the only place that knows a screen's locators. Tests talk to it in plain actions.

What it is

Each screen gets a class. The class holds the screen's locators and offers actions like loginAs(email, password). In a hybrid framework, each platform has its own page class, and all of them implement one shared interface such as LoginView. A small page factory picks the right class, so tests never choose it themselves.

Why you need it

When a locator changes, you fix it in one file instead of in every test that touches that screen. Try the slider to see the difference.

See it: a login button's locator changes

How to do it

  1. One class per screen, per platform: WebLoginPage, NativeLoginScreen.
  2. Locators are private. Only actions and simple state checks are public.
  3. Actions describe user intent: loginAs(), not clickButton3().
  4. Do not put business assertions in pages. A page may offer expectLoaded(). The test decides what "correct" means.

Test data: JSON, Excel, CSV, database, API

Tests ask for data by meaning ("an admin user"). A repository decides where it comes from.

What it is

Three patterns work together here:

Repository
The only code that reads test data. Tests call users.get("admin"), never "row 4 of sheet 2."
Source
A small reader for one format: JSON, Excel, CSV, a database or an API. The repository uses a source and hides it.
Builder
Creates complex objects with safe defaults, so each test sets only the fields it cares about.

Data-driven testing runs one test body many times, once for each row of data.

Why you need it

Shared, hard-coded data is one of the biggest causes of flaky tests. Test A changes the account that test B needs. With a repository, you can move from Excel to JSON, or from JSON to an API, without touching a single test.

export async function readSheet(path: string, sheet: string): Promise<Record<string, string>[]> {
  const workbook = new ExcelJS.Workbook();
  await workbook.xlsx.readFile(path);
  const ws = workbook.getWorksheet(sheet);
  if (!ws) throw new Error(`Sheet not found: ${sheet}`);

  const headers = (ws.getRow(1).values as unknown[]).slice(1).map(String);
  const rows: Record<string, string>[] = [];
  ws.eachRow((row, rowNumber) => {
    if (rowNumber === 1) return;
    const values = (row.values as unknown[]).slice(1);
    rows.push(Object.fromEntries(headers.map((h, i) => [h, String(values[i] ?? '')])));
  });
  return rows;
}

Hooks set things up before a test and clean up after it, even when the test fails.

What it is

A hook is code that the runner calls at a fixed moment: before all tests, before each test, after each test, after all tests. Each runner names them differently:

If cleanup lives inside the test, it never runs when the test fails early. Then drivers stay open, devices stay locked and the next test fails too. Hooks always run, so evidence is captured and resources are released.

Gherkin describes behavior in business words. Step definitions translate those words into framework calls.

What it is

BDD (Behavior-Driven Development) is a way to agree on behavior using examples. The examples are written in Gherkin: Given a starting state, When an action, Then an expected result. What it is

Locator strategy for web, mobile and desktop

A good locator finds the element by its purpose, not by its position on the screen.

What it is

A locator tells the tool which element to use. Some locators survive redesigns. Others break when a developer adds one <div>. Each platform has its own best options.

Why you need it

Weak locators are a top cause of flaky and broken tests. A positional XPath like //div[3]/div[2]/button breaks when the layout changes, even if the feature still works.

See it: priority by platform

How test IDs get added

  1. QA names the element in the ticket and proposes an id that follows the rule: lowercase, hyphens, describes the purpose, such as checkout-submit.
  2. The developer adds the attribute in the same pull request as the feature: data-testid on web, accessibilityIdentifier on iOS, contentDescription or a resource id on Android, AutomationId on Windows.
  3. The page object uses the id in that same pull request.
  4. Adding test ids is part of the definition of done for any new screen.

Watch out

  • Avoid generated class names, positional XPath and anything tied to layout.
  • On Android, contentDescription is also read aloud by screen readers. Do not put technical ids where users will hear them. Agree on resource ids for test-only names.
  • Web semantic locators (role and label) also catch accessibility problems. Test ids are better for localized text and complex widgets. Record your team's choice in an ADR (Architecture Decision Record).

Anti-flakiness: why tests pass, then fail, with no code change

A flaky test sometimes passes and sometimes fails on the same code. Flaky tests destroy trust faster than missing tests.

What it is

A test is flaky when its result depends on something other than the product: timing, shared data, test order, the network or the machine. The fix is almost never "add a longer sleep." The fix is to remove the hidden dependency.

Why it matters

When a suite is flaky, people stop reading failures. They click "re-run" until it turns green. Then a real bug fails the build and everyone re-runs that too. A flaky test is not a small problem. It trains the team to ignore the suite.

See it: hard sleep vs waiting for state

Both tests click "Save," then check for "Saved." The server's response time changes a little on every run, like a real environment. Move the slider to make the server slower, then run 30 times.

See it: the common causes and their fixes

The core rules

  1. Never use fixed sleeps. Enforce it with a lint rule or a CI check.
  2. Wait for state, not time: a visible message, an enabled button, a network response.
  3. Use stable locators (topic 21).
  4. Give each test its own data and do not let tests depend on each other.
  5. Set up through the API, not the UI.
  6. Retry assertions, never actions. The framework can check "is it Completed yet?" many times. It must never click "Place order" twice.
  7. Fail fast. Check that the page is ready before you start. A clear early failure beats a confusing late one.
  8. Control the environment: fixed timezone, seeded random values, animations disabled in test mode.

Each tool waits differently. Your framework should make the right wait the easy default.

What it is

Playwright already waits before it clicks or types. It checks that the element is visible, stable, enabled and able to receive events. Appium and Selenium do not. They act immediately unless you add an explicit wait. This is why a hybrid framework puts waits inside the driver adapter. Pages and tests then never think about timing.

Why you need it

If every test author writes their own waits, some will use sleeps, some will forget, and some will wait for the wrong thing. One adapter, written once and reviewed carefully, fixes timing for every test on that platform.

export class AppiumDriver implements UiDriver {
  constructor(private readonly driver: Browser, private readonly timeout = 15_000) {}

  private async ready(target: string, mustBeEnabled: boolean) {
    const el = this.driver.$(target);
    await el.waitForDisplayed({ timeout: this.timeout, timeoutMsg: `Not visible: ${target}` });
    if (mustBeEnabled) {
      await el.waitForEnabled({ timeout: this.timeout, timeoutMsg: `Not enabled: ${target}` });
    }
    return el;
  }

  async type(target: string, text: string) { await (await this.ready(target, true)).setValue(text); } // clears first
  async textOf(target: string) { return (await this.ready(target, false)).getText(); }
  async waitVisible(target: string) { await this.ready(target, false); }
  async screenshot() { return Buffer.from(await this.driver.takeScreenshot(), 'base64'); }
  async quit() { await this.driver.deleteSession(); }
}

    }

    private WebElement clickable(String id) {

                   .until(ExpectedConditions.elementToBeClickable(AppiumBy.accessibilityId(id)));

Code: polling for work that finishes later

Polling is not a blind sleep. It checks the real state, stops at a deadline and explains the failure, including the last value it saw.

// For work that finishes later: an order moving from "Processing" to "Completed"
public static async Task PollUntilAsync<T>(
    Func<Task<T>> read, Func<T, bool> isDone, TimeSpan timeout, TimeSpan interval, string what)
{
    var deadline = DateTimeOffset.UtcNow + timeout;
    T last = default!;
    while (DateTimeOffset.UtcNow < deadline)
    {
        last = await read();
        if (isDone(last)) return;
        await Task.Delay(interval);   // controlled polling interval, not a blind sleep
    }
    throw new TimeoutException($"Timed out after {timeout} waiting for {what}. Last value: {last}");
}

// For work that finishes later: an order moving from "Processing" to "Completed".
// (The Awaitility library does the same thing with a fluent API.)
public static <T> T pollUntil(Supplier<T> read, Predicate<T> isDone,
                              Duration timeout, Duration interval, String what) {
    Instant deadline = Instant.now().plus(timeout);
    T last = null;
    while (Instant.now().isBefore(deadline)) {
        last = read.get();
        if (isDone.test(last)) return last;
        try {
            Thread.sleep(interval.toMillis());   // controlled polling interval, not a blind sleep
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("Interrupted while waiting for " + what, e);
        }
    }
    throw new AssertionError("Timed out after " + timeout + " waiting for " + what + ". Last value: " + last);
}

Retries, flaky tracking and quarantine

Retries handle infrastructure hiccups. They must never hide product bugs.

What it is

A retry runs a failed test or step again. Quarantine moves a known-flaky test out of the blocking build, so it stops blocking pull requests. It still runs and reports in a separate job.

Why you need rules

Without rules, retries turn every flaky failure into a silent pass, and the flakiness grows. With rules, a test that passes only on retry is reported as flaky, and somebody owns fixing it.

See it: retry policy

A state-changing action (pay, submit)Never automaticallyRepeating it can create duplicate data

// Retry INFRASTRUCTURE (starting a session), never the test's own steps.
// Note: NUnit's [Retry] re-runs a test after a failed ASSERTION, which can hide
// real bugs. Prefer this narrow retry around driver creation.
public static async Task<IUiDriver> CreateWithRetryAsync(TestConfig c, int attempts = 2)
{
    for (var attempt = 1; ; attempt++)
    {
        try { return await DriverFactory.CreateAsync(c); }
        catch (Exception ex) when (attempt < attempts && ex is WebDriverException or PlaywrightException)
        {
            Log.Warn($"Session start failed (attempt {attempt}/{attempts}): {ex.Message}");
            await Task.Delay(TimeSpan.FromSeconds(2 * attempt));   // back off
        }
    }
}

Reporting, observability and the Observer pattern

A good failure answers four questions fast: what failed, where, when, and why.

What it is

Observability means a failed test leaves enough evidence to understand it without running it again: a screenshot, a trace or video, logs, a network record, plus the build, browser or device, and environment. The Observer pattern delivers this. When a test finishes, one event goes out. Several listeners react: one saves a screenshot, one attaches logs, one notifies the team.

Why you need it

If a failure needs a re-run to understand, people re-run instead of investigating. Good evidence makes the time to diagnose a failure drop from an hour to a minute.

See it: one event, many listeners

How to do it

  1. Send everything to one folder: output/junit, output/html, output/test-results, output/logs.
  2. Use JUnit XML as the one machine-readable format for CI, plus an HTML or Allure report for people.
  3. Capture heavy evidence (video, trace) on failure only, to save time and storage.
  4. Track metrics over time: first-attempt pass rate, flaky rate, suite duration, quarantine count and age.

Code: observer for test events

Your runner already uses this pattern. Playwright reporters, pytest hooks, NUnit event listeners and JUnit's TestExecutionListener are all observers. Plug into those first. The code below shows the idea in its simplest form.

Parallel execution and CI/CD

Parallel runs make the suite fast. CI makes it run on every change. Both need isolated tests first.

What it is

Parallel execution runs tests at the same time on several workers. Sharding splits the suite across several machines. CI/CD runs the right tests at the right moment: on each pull request, on merge, on a schedule and after deployment.

Why you need it

Feedback that takes hours is ignored. Feedback in minutes changes how developers work. Parallel runs are also an architecture test: they expose every bit of shared state you forgot about.

See it: estimate your run time

A simple model: total test time divided by workers, plus fixed overhead. Real runs are a little slower, because tests are not all the same length.

See it: a typical pipeline

Parallel safety checklist

  • Unique data per test, and no test depends on another.
  • A browser context, device or app session per test or per worker.
  • Output file names that cannot collide between workers.
  • Locks or pools for shared resources: one payment sandbox, a few promo codes.
  • Worker count matched to what the environment, the devices and the backend can handle.

Security and production safety

Test code touches real systems and real credentials. Treat it like production code.

Rules

  • Use synthetic test data only. Never use copies of real customer data.
  • Store secrets in the CI secret store or a vault, such as Azure Key Vault or AWS Secrets Manager. Prefer short-lived identities over long-lived keys.
  • Treat logs, traces, screenshots, videos and HAR files as sensitive.
  • Run destructive tests only in approved non-production environments.
  • Run production checks only when approved: read-only, with synthetic accounts.
  • Never turn off TLS certificate checks as a shortcut.
  • Do not pass tokens as command-line arguments, because they appear in process lists and logs.
  • Scan dependencies regularly and rotate test credentials on a schedule.
